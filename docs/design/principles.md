# 宪法级精神原则

> 项目精神宪法。下游设计、实现、配置以本文为标准。冲突时改下游不改本文。

---

## 一、根本问题意识

当前 Rust 验证工具生态高度分化，每个工具各有声明形式、测试方法、特性覆盖说明，工具间不可比较。社区缺一个工具无关的特性覆盖测量框架。要做这样一个框架，存在两条根本性问题，任一被破都让测量失公信力。

### 根本问题 1：不公平

任一既有路径——把样例改成工具特定形态、或把样例围绕统一抽象 API 写——都把"不公平"沉淀进样例本身：样例污染、抽象成新依赖、每加一工具都要改样例。

**对策**：把不公平沉淀到第三方中介层（runner + 配置 + 模板），让样例与工具两端各自纯粹。

### 根本问题 2：不公信（不引发纠纷）

测量是对外可见的工具能力筛查。若测量姿势工具开发者可一句话驳回——"你姿势不对" / "这不是我们设计来支持的用法"——测量失公信力。

**对策**（自上而下三条次序）：

1. **本地性 / 当前性**（最高）：测当下这个工具版本 + 它所要求的 toolchain 能做什么。装对其要求的 toolchain 后仍不行 → 工具菜，FAILED 站得住
2. **遵循社区惯例**：在本地性之下，用工具开发者文档化 / 推荐 / 默认的用法；不钻牛角尖、不测预期外姿势
3. **最大善意**：在能做的姿势内尽力配合（装其要求 toolchain、按其文档姿势用工具、测其用户实际遇到的特性）

最大善意尽到后工具仍失败 → FAILED 有公信力，工具开发者不能驳回。

### 二者关系

- 不公平：对工具两两间公平（中立性）
- 不公信：测量结果对外站得住（对社区惯例 + 本地性对齐）
- 两条问题都是宪法级，下游任一冲突必须改下游，不改本文

## 二、项目目标、范围、价值

**目标**：构建工具特性覆盖率测试框架，通过样例驱动方式测量与比较 Rust 工具的特性覆盖。

**范围**：项目目标是框架；测试报告是框架的应用产物，随工具版本浮动。工具能力的客观判定不在项目范围。

**生效约束**：本宪法约束本项目下游的设计、实现、配置（架构 / 细化 / runner / tools / examples / 测试报告）。第三方复用本框架时只需遵守 §四 核心原则与 §三 模块二分；§五 / §六 / §七 是本项目自身的方法学选择，外部复用不受其约束。

**不可妥协价值**：

1. 样例与工具两端不可被中介层侵入（破中立或破黑盒）
2. SUCCESS 信号必须诚实（不冤枉、不藏盲点）
3. 测试结果必须可重现（脱离时间 + 工具版本上下文的结论无效）
4. 测量姿势对社区惯例 + 本地性对齐（最大善意尽到后的 FAILED 才入册）

## 三、模块定位

项目分两类模块：

- **核心模块**（长期承诺）：runner（测试运行与结果分析）+ examples（样例库）
- **次要模块**（应用展示，非长期承诺）：tools 集成 + 实测报告

## 四、核心原则

### 原则 A：双方都不可侵入

样例源码（src/ + Cargo.toml + entry fn body）不为工具改动；工具作为黑盒，不为框架适配。异质性必然落到第三方框架。

**A 的形式定义**：信号文件（`hirusttest.toml` 或 `.hirusttest/`）加入前后，example 的 cargo 行为字节级一致。

**A 的双轨 schema**（工程自决）：

- 简单（仅 entries + 少量字段）→ 单文件 `hirusttest.toml`
- 复杂（需 per-entry 辅助文件或 schema 写不下）→ 目录 `.hirusttest/`

### 原则 B：测必要条件，非语义对错

只问"工具能不能吃下这段代码并产出预期形状的输出"，不问"产出语义是否正确"。分类标签只描述产出形状，不带对错评分。

B 的等距推论：测"接受 vs 不接受"，不区分翻译深浅（浅 syntactic 搬运 / 深 MIR 翻译 / verifier dialect 接受一律不加权）。

### 原则 C：异质性归配置，框架代码同质

工具间差异以声明数据（`tool.toml` + tera 模板）存在，不作为框架代码的 if 分支。任何 `if tool == "kani"` 都被禁止。

## 五、核心模块的精神

### runner：结果记录严谨全面

每次 run 必须记录 (工具版本, 测试环境, ISO 时间戳, 样例特征) 四元组，作为裸数据自描述存入 `results.json`。脱离上下文的结果不可重现。

### examples：纯净性 + 多样性

- **纯净性**：每 entry 一个独立 lib crate，零 verifier 标记，无跨 entry 共享 helper
- **多样性**：样例覆盖单特性、边界（`*-limit/`）、综合（如 `industrial/`）多个梯队

---

## 六、次要模块的精神

### 时空锚定

工具能力观察必须锚定 (工具版本, 时间) 二元组。工具升级后旧结果的解释力衰减，是必然的、不是缺陷。测试报告不构成对工具能力的长期承诺。

### Oracle 责任

- **不冤枉**：SUCCESS 必须是真 SUCCESS——不允许任何 partial / silent skip / 半翻译；工具自陈"我没全干完"必须被尊重
- **不藏**：已知漏报盲点必须文档化
- **UNKNOWN 严格语义**：UNKNOWN 只在两类场景使用——(a) 全局工具链崩溃（重装可修），(b) 我们这边可识别的问题且暂未修（如我们 harness 模板 bug / 我们 corpus 引入的 vendored crate lint / 我们环境损坏）。每类必附明确归因 + 会修计划。**官方 wrapper 失败 / 工具自选 toolchain 不支持新特性 / 工具单文件 pipeline 不读 Cargo.toml / 官方 wrapper 不传 --edition** 一律 FAILED——这些是工具自身能力边界，按"本地性原则"FAILED 站得住，工具开发者不能驳回

### 前端测量

工具能力的测量限于工具自身前端（parser / 类型检查 / 翻译 / 模型构造），求解层不计入。测必须命中工具自身前端，而非 rustc 等代理前端——否则 SUCCESS 信号退化为"rustc parses it"，丢失工具间分化。

## 八、审查协议（先反后反反）

任何对本宪法 / 下游派生（架构 / 细化 / 实施）的审查必须满足：

1. **独立审查者**：审查者不是制定者本人 / 不在同一讨论上下文（独立人 / 独立 agent / 跨 session AI）
2. **先反立场（挑刺）**：审查者用反立场挑刺，给具体理由 + 文件位置 + 引用
3. **后反反立场（counter-challenge）**：派另一独立 agent / 第三方按挑刺逐条 counter
4. **counter-challenge 方法**：**反复高强度审视精神性陈述**——精神已明示则挑刺不成立 / 精神没明示则挑刺成立
5. **挑刺只在 counter-challenge 站不住后才落地**

**实用主义经验理由**：LLM 单边挑刺常发现问题（高 recall），confirmation 几乎无效。反两次过滤低效挑刺（high precision），反三次以上边际递减。这是经济上的最优点，**不是绝对真理**——是基于实用主义经验作为推荐性公理。

**审查 / 自修改的工作流**：审查产出必须按 `/workflow` skill 区分 **决策点 vs 非决策点**。可以没有决策点（全是非决策性改动），但必须明示这种区分。

详细方法学：参考 `charter-craft` skill §4.8。
