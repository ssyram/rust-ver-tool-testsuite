## §1 问题意识

用户在多次 D3 / 元反思后明确了一个判断：**宪法应当直陈性 + 正交性 + 不修修补补**。

但当前 `principles.md` 319 行——其中真正"不可推导、必须直陈、彼此正交"的核心精神大概只占 1/3 体量。剩下的体量是：

1. **同一精神的不同侧写**（"自身完善独立" / "极简解耦" / "标识性信号上限" 反复说同一件事，只是从不同角度）
2. **派生原则的二次细化、三次细化**（A 的 5 层精细化等——派生应该一刀切到下层，不该写进宪法）
3. **工程现实判断**（什么算"复杂 schema"什么算"简单 schema"——这是工程师工作时自决的，不该入宪）
4. **enumerate 数字**（"19 工具"、"5 层"、"3 大原则"、"4 条硬指标"——这些数字随时间漂移，刻在宪法里就形成"数字债"）
5. **流程指令**（discover 顺序、runner 报错责任——这些属 detailed-design）
6. **典型的"原则 + 例外"语法**（"原则上 X，但是 Y 情况下 Z"——这是直陈性的反模式）

本审用**奥卡姆 + 直陈性**两标准重审。

## §2 审查方法

### 2.1 奥卡姆剃刀准则

宪法最重要的是**说清楚 + 直陈性**，从而**让后面的落地原则可以直接从里面检查 / 导出**。任何"不必要的条款"都该剃。

**剃什么**（用户清单）：

- 重复表述同一精神的不同条款（同义反复）
- 派生原则的过度细化（5 层精细化等——派生该一刀切到下层）
- 工程现实判断（什么算"复杂"什么算"简单"——下层自决）
- enumerate 数字（"19 工具" / "3 件套"——数字会变）
- 流程指令（"按 X 步骤做 Y"——流程在 detailed-design）
- 任何能在 architecture / detailed-design 里说而不影响精神的细节

**保留什么**：必须直陈、不能从下层推导、彼此正交的核心精神。

### 2.2 直陈性准则

**直陈性 = 正向论证无例外**。

反模式（"K 事情原则上应当 A，但 X 情况下允许 B"）违反直陈性。

**正确模式**：把 K 分解为 Y 和 X 两种本质不同情况（**disjoint union 不相交并 + 两侧都用直接定义而非补集**），从而得到两条平行规则：

- Y → A
- X → B

这考验**对问题的分解能力**——真正想清楚 K 实际上是几种本质不同情况的合集。

**实例**（D3 已落地）：

❌ 旧："外部综合项目原则上必须用目录轨，但简单单特性测试不允许升级到目录轨"
✅ 新：双轨按 schema 复杂度自决——简单（只需 entries + 少量字段）→ 单文件轨；复杂（需 per-entry 辅助文件或 schema 写不下）→ 目录轨

D3 已剃了"双轨例外"——但宪法其它部分还有不少类似主从结构待剃。

### 2.3 与 audit-1 / counter-1 的关系

Audit-1 提了 4 条修宪议案——counter-1 用 disprove-first 全部驳回。**但 counter-1 是"驳斥补充修宪"，没有考虑"减法 / 重构修宪"**——也就是说，那 5 个 audit 都在问"还要不要加点什么"，没人问"现有的能不能更纯"。

本审补这个方法论缺口：**用奥卡姆做减法、用直陈性做重构**，目标是篇幅减半到三分之一、可逐条溯源、零"原则+例外"。

### #1 (剃)　§三 模块定位的 "first-class / non-first-class" 标签

## 一、根本问题意识

当前 Rust 验证工具生态高度分化，每个工具各有声明形式、测试方法、特性覆盖说明，工具间不可比较。
社区缺一个工具无关的特性覆盖测量框架。

已有路径（把样例改成工具特定形态、或把样例围绕统一抽象 API 写）都把不公平沉淀进样例本身。

**本项目的核心意识**：把不公平沉淀到第三方中介层（runner + 配置 + 模板），让样例和工具两端各自纯粹。

---

## 二、项目目标

构建工具特性覆盖率测试框架，通过样例驱动方式测量与比较 Rust 工具的特性覆盖。

项目目标是框架；测试报告是框架的应用产物，随工具版本浮动。

---

## 三、模块定位

项目分两类模块：

- **核心模块**（长期承诺）：runner（测试运行与结果分析）+ examples（样例库）
- **次要模块**（应用展示，非长期承诺）：tools 集成 + 实测报告

---

## 四、核心原则

### A. 双方都不可侵入

样例源码（src/ + Cargo.toml + entry fn body）不为工具改动；工具作为黑盒，不为框架适配。
异质性必然落到第三方框架。

**A 的形式定义**：信号文件（hirusttest.toml）加入前后，example 的 cargo 行为字节级一致。

**A 的双轨 schema**：
- 简单（仅 entries + 少量字段）→ 单文件 hirusttest.toml
- 复杂（需 per-entry 辅助文件或 schema 写不下）→ 目录 .hirusttest/

### B. 测必要条件，非语义对错

只问"工具能不能吃下这段代码并产出预期形状的输出"，不问"产出语义是否正确"。
分类标签只描述产出形状，不带对错评分。

### C. 异质性归配置，框架代码同质

工具间差异以声明数据（tool.toml + tera 模板）存在，不作为框架代码的 if 分支。

---

## 五、核心模块的精神

### runner：结果记录严谨全面

每次 run 必须记录 (工具版本, 测试环境, ISO 时间戳, 样例特征) 四元组。
脱离上下文的结果不可重现。

### examples：纯净性 + 多样性

- **纯净性**：每 entry 一个独立 lib crate，零 verifier 标记，无跨 entry 共享 helper
- **多样性**：样例覆盖单特性、边界（*-limit/）、综合（industrial/）多个梯队

---

## 六、次要模块的精神

### 时空锚定

工具能力观察必须锚定 (工具版本, 时间) 二元组。
工具升级后旧结果的解释力衰减，是必然的、不是缺陷。

### Oracle 责任

- **不冤枉**：SUCCESS 必须是真 SUCCESS（不允许任何 partial / silent skip / 半翻译）
- **不藏**：已知漏报盲点必须文档化

### 前端测量

工具能力的测量限于工具自身前端（parser / 类型检查 / 翻译 / 模型构造）。
求解层不计入。测必须命中工具自身前端，而非 rustc 等代理前端。

### 不区分翻译深浅

工具自身前端在册收下即算"接受"——浅 syntactic 搬运、深 MIR 翻译、verifier dialect 接受一律不区分。

---

## 七、外围原则

### 问题范围

本项目 v1 范围只解决功能层面问题。
性能、资源用量、缓存效率不在 v1 范围。
